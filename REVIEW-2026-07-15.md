# Ревизия murm386 — 2026-07-15 (статический анализ)

Дифф: `murm386-review-2026-07-15.diff` (против murm386.zip; включает применённый
patch.diff от Mike + мои изменения поверх).

## 1. Верификация анализа chatGPT по вложенному EXEC (task.c)

Подтверждено по коду, принято с одной поправкой:

**Принято как есть:**
- `cpu->native_done` не входил в `exec_child_context` и безусловно обнулялся на
  входе И на выходе. Это общий сигнальный канал трёх пользователей
  (`request_terminate()`, waiter'ы `bios_intcall()` и `cpu_far_call()`), и при
  цепочке «гостевой родитель (VC) → native FCOM → гость (CHECKIT)» внешнее
  состояние затиралось. Теперь `native_done` — часть контекста уровня:
  сохраняется в `exec_enter_child()`, восстанавливается в `exec_leave_child()`.
  Тот же save/restore добавлен в `bios_intcall()` и `cpu_far_call()` (они
  обнуляли его на выходе тем же образом).
- `EXEC_PROCESS_NATIVE_COMMAND` вызывал `request_terminate()` — категориальная
  ошибка: у native FCOM нет собственного `pc_step()`-цикла, и
  `native_done = true` адресовался активному циклу *чужого* (внешнего
  гостевого) уровня, давая импульс true→false внутри него. Теперь путь native
  просто записывает `term_exit_code/term_exit_type` (то, что `return_user()`
  оставляет для AH=4Dh родителя) — без сигнализации CPU-циклу.
  `exec_release_child()` читает `term_exit_type` для решения о keep-resident,
  поэтому тип на этом пути выставляется явно (0).

**Скорректировано (отличие от предложения chatGPT):**
- `term_exit_code`/`term_exit_type` НЕ включены в per-level контекст и их
  обнуление на входе EXEC **удалено**, а не заменено на save/restore.
  Обоснование: upstream FreeDOS хранит статус AH=4Dh в ЕДИНОЙ глобальной
  переменной (SDA), не очищая её при старте нового ребёнка. Save/restore на
  уровень сделал бы статусы независимыми стековыми — это НЕ семантика DOS:
  (а) статус предыдущего sibling-ребёнка обязан переживать неудачный запуск
  следующего; (б) статус, оставленный ребёнком, обязан переживать
  `exec_leave_child()`, чтобы родитель прочитал его 4Dh-ом. Вложенность при
  единой глобали корректна ровно потому, что каждый уровень потребляет статус
  сразу (patch.diff добавил `capture_exec_status()` с чтением 4Dh после
  каждого EXEC — это закрывает вопрос).

## 2. patch.diff: применён, замечания по слиянию и ревизии

- Применён с ручным слиянием 3 конфликтов (патч сделан до моих правок):
  раскладка блока теперь `ENTRY(2) + TERM(INT 20h, 2) + CBREAK-стаб(9) +
  CBreakCounter(2)`; в `fcom_process_main()` их init-блок (self-parent,
  terminate hook PSP:0Ah, COMSPEC) объединён с моей установкой вектора 23h.
- Замечания (не блокирующие, для сведения):
  - `capture_exec_status()` при ошибке EXEC пишет `errorlevel = -rc`
    (например, 2 для file-not-found) с `exit_reason 0xff`. У оригинального
    FreeCOM errorlevel при неудачном запуске ведёт себя иначе (не
    перезаписывается кодом ошибки загрузки) — стоит сверить с
    shell/command.c при случае.
  - Хук INT 20h по PSP:0Ah структурно верен (как у настоящего FreeCOM), но в
    порту на вектор/адрес 22h при завершении никто не прыгает — сейчас это
    «спящий» код. Безвреден.

## 3. Ранее внесённое в этой ревизии (сводка)

- **/P=\FDAUTO.BAT**: `fcom_create_process()` считал ctCount как `strlen`,
  захватывая `"\r\n"` из `Config.cfgInitTail` → путь автозапуска получал
  хвост `\r\n` и open молча падал. Теперь скан до `'\r'` (форма цикла
  upstream `prep_shell()`).
- **Ctrl+C → no_handled (FFE0:0023)**: отсутствовал аналог `init_vectors()`
  из main.c. Добавлен `setup_int_vectors()` (kernel.c): IRET-дефолты
  22h..3Fh кроме нативных 25h–29h/2Fh/30h/31h/33h; INT 24h → байты
  `mov al,FAIL; iret` на F000:FF44 (кладёт pc.c, как `_int24_handler` из
  kernel.asm).
- **handle_break**: реализован протокол `spawn_int23` (procsupt.asm):
  равный SP (IRET/RETF 2) ⇒ resume с игнором CF; RETF 0 + CF=1 ⇒ terminate
  (`request_terminate(0,1)`), иначе resume. Добавлен `terminate_requested()`
  и guard'ы в I/O-циклах chario.c (upstream-код стоит после noreturn).
- **INT 23h native FCOM**: настоящий гостевой стаб `inc [cs:cnt]; clc;
  retf 2` (cb_catch.asm) + `CBreakCounter` в гостевой памяти; порт
  `chkCBreak()` со всеми точками опроса оригинала (batch.c:533, 406, 223;
  cmdinput.c:188) и промптом «Terminate batch file '%s' (Yes/No/All) ?».
- **LH/LOADHIGH**: полный порт shell/loadhigh.c (в оригинале включён
  INCLUDE_CMD_LOADHIGH; FAKE-вариант — закомментирован upstream'ом):
  findUMBRegions/parseArgs(/L,/S)/loadhigh_prepare/lh_lf на прямых вызовах
  ядра (DosMemAlloc/DosUmbLink/mem_access_mode, FIRST_FIT_U=0x80 — численно
  совпадает с оригиналом). LOADFIX оставлен на прежнем отдельном пути.
- **Norton/INT 1** (трассировка прерываний через TF): канонические IBM AT
  точки входа BIOS в F000 (13h→E3FE, 10h→F065, 15h→F859 и др.) — 5-байтовые
  `JMP FAR FFE0:NN`, чтобы трассировщик на первом же шаге видел CS=F000;
  подавление отложенного TF-трапа после программного INT (как на реальном
  CPU); `was_TF` → файловый `pending_ss_trap` c save/restore через
  вложенный `bios_intcall()` (изоляция single-step состояния уровней).

## 4. Открытые пункты (требуют runtime/трассировок — вне этой сессии)

- Norton main menu → срыв core1 (VGA): статически причина не видна; нужен
  ring-buffer лог VGA-регистров/режимов на момент срыва.
- bios_09h не вызывает вектор INT 1Bh (только ставит защёлку 0040:0071) —
  гостевые хуки Ctrl-Break мертвы; нужен callback-стаб по образцу INT 15h/4Fh.
- INT 24h у native FCOM — стоит портировать criter (Abort/Retry/Fail UI);
  сейчас действует кернельный дефолт FAIL.
- wolf3d — без изменений, отдельное расследование (вероятно 386-путь/EMS).
- errorlevel при неудачном EXEC (см. §2) — сверить с оригиналом.
